## 3. Flujo de Autenticación JWT + 2FA

```mermaid
sequenceDiagram
    autonumber
    actor U as Usuario
    participant FE as React SPA
    participant BE as FastAPI
    participant DB as PostgreSQL
    participant TOTP as pyotp (TOTP)

    U->>FE: Ingresa credenciales + OTP
    FE->>BE: POST /api/v1/auth/login
    BE->>DB: SELECT usuario WHERE email=? (hash)
    DB-->>BE: Retorna usuario + rol + secret TOTP
    BE->>TOTP: pyotp.TOTP.verify(OTP)
    alt OTP Válido
        TOTP-->>BE: True
        BE-->>FE: { access_token, refresh_token, role }
        FE->>FE: Guarda token en localStorage
        FE-->>U: Redirige al dashboard por rol
    else OTP Inválido
        TOTP-->>BE: False
        BE-->>FE: 401 Unauthorized
        FE-->>U: Mensaje de error genérico (sin revelar campo fallido)
    end
```

## 4. Regla de Oro: Offloading de PDF (Protección de RAM)

El servidor Orange Pi 5 opera con **1GB de RAM compartida** entre Nginx, FastAPI con Gunicorn (workers), y el Wazuh Indexer. La generación de PDFs grandes en el servidor causaría OOM (Out of Memory) en producción. Esta es una **decisión arquitectónica irrevocable**.

```mermaid
flowchart LR
    A["👤 Analista hace clic<br/>en 'Generar PDF'"] --> B["⚛️ React — PdfGenerator.js<br/>jsPDF + AutoTable<br/>100% en navegador"]
    B --> C["📄 PDF generado<br/>Descarga automática al disco"]
    
    D["❌ FastAPI — PROHIBIDO<br/>No renderiza PDFs"]
    
    style B fill:#d4af37,color:#0d1117,stroke:#d4af37
    style D fill:#f85149,color:#e6edf3,stroke:#30363d
```

| Estrategia | Dónde se procesa | RAM del servidor consumida | Estado |
|---|---|---|---|
| PDF Client-Side (jsPDF) | Navegador del cliente | 0 MB adicional | ✅ Obligatorio |
| PDF Server-Side | FastAPI / Gunicorn | 200-500 MB por solicitud | 🚫 Prohibido |

## 6. Entornos de Despliegue

| Entorno | Archivo Docker Compose | Características Clave | Notas de Seguridad |
|---|---|---|---|
| **Desarrollo** | `docker-compose.override.yml` | Live Reload (Vite/Uvicorn), Mocks habilitados | Puertos internos expuestos para debug (`8000`, `5173`) |
| **Staging** | `docker-compose.yml` | Cloudflare Tunnel, datos reales limitados | Sin puertos expuestos al host público |
| **Producción** | `docker-compose.prod.yml` | Multi-Stage builds, Gunicorn con Uvicorn workers | Non-root users, TLS termination en CF |

> [!CAUTION]
> **Regla de seguridad explícita:** Las bases de datos (PostgreSQL, Wazuh Indexer) **JAMÁS** exponen puertos al host en `docker-compose.prod.yml`. El mapeo `5432:5432` o `9200:9200` está explícitamente prohibido. Solo Nginx expone los puertos necesarios internamente (o al host si CF Tunnel no lo absorbe).

```jsx
// src/layout/RoleGuard.jsx
import { useContext } from 'react';
import { AuthContext } from '@/context/AuthContext';

export const RoleGuard = ({ allowedRoles, children, fallback = null }) => {
  const { user } = useContext(AuthContext);
  if (!user || !allowedRoles.includes(user.role)) return fallback;
  return children;
};
```

# 🏗️ Regla de Arquitectura Desacoplada (API-First)

Para el desarrollo del proyecto HoneyMetrics, el Agente debe hacer cumplir **estrictamente** las siguientes normas de arquitectura, inspiradas en las mejores prácticas de infraestructura moderna (DevOps):

1. **Cero Monolitos:** Prohibido el uso de Django Templates (`render()`, `TemplateResponse`) para la UI de usuario final. Django **solo** actuará como un proveedor de API JSON/REST.
2. **Repositorios Aislados:** El código del Frontend (React, Angular, Vue) nunca debe mezclarse en este mismo repositorio. Si el usuario intenta agregar código frontend a este repositorio, el agente debe detenerlo y recordarle clonar o inicializar un repositorio separado.
3. **Manejo de CORS y Nginx:**
   - La comunicación entre Frontend y Backend en producción se gestionará a través de un proxy reverso (Nginx).
   - Nginx servirá los archivos estáticos de la Single Page Application (SPA) en la raíz (`/`) y hará proxy a Django exclusivamente en las rutas `/api/` y `/admin/`.
4. **Despliegue Seguro (Docker):**
   - El entorno de Docker usará Dockerfiles Multi-etapa (Builder pattern).
   - El proceso de Django se ejecutará bajo un usuario sin privilegios (`non-root`) dentro del contenedor.
   - Las bases de datos y otros servicios internos JAMÁS expondrán puertos al host en los archivos `docker-compose.prod.yml` (ej. mapeos como `1435:1433` quedan estrictamente prohibidos).
5. **Autenticación Desacoplada:** Reemplazar el uso de `SessionAuthentication` clásico de Django por `JWT (JSON Web Tokens)` mediante `djangorestframework-simplejwt` u otro proveedor stateless, para permitir el consumo seguro desde el frontend.

# 🚫 Reglas Inquebrantables del Director de Proyecto (Scrum & Product)

Estas son las reglas supremas que gobiernan la redacción técnica en este repositorio. Su incumplimiento significa el rechazo automático del entregable.

1. **Cero Sesgo Técnico en el Backlog:** Jamás escribas el "CÓMO" (bases de datos, endpoints, librerías) en la hoja de Product Backlog. Solo se redacta el "QUÉ" y el valor de negocio.
2. **Desacoplamiento de CRUDs:** Prohibido hacer un CRUD completo en una sola Historia de Usuario. Debe partirse en "Listar", "Crear", "Editar" y "Eliminar".
3. **Criterios de Aceptación Gherkin:** Prohibidos los bullet points libres. Todo criterio es: `Dado que... Cuando... Entonces...`.
4. **Estimación Fibonacci:** Solo se acepta `1, 2, 3, 5, 8, 13, 21`. HU mayores a 13 puntos deben rebanarse (Vertical Slicing).
5. **Diagramación Viva:** Toda arquitectura, flujo o entidad-relación DEBE ser dibujada mediante código (Mermaid.js). Las imágenes estáticas solo se permiten para mockups de Interfaz de Usuario.

# 🖥️ Regla de Hardware y Topología Distribuida (Wazuh y FastAPI)

Para el desarrollo del proyecto HoneyMetrics v2.0, el Agente debe respetar las siguientes restricciones de infraestructura:

1. **Nodos Separados (LAN):** 
   - **Nodo A (Intocable):** Wazuh (OpenSearch) se aloja en `192.168.32.11:9200`. NO se despliega código aquí.
   - **Nodo B (Backend Activo):** La API de FastAPI y PostgreSQL se alojan en el equipo con IP `192.168.31.112` (16GB de RAM).
2. **Protección de Memoria (Anti-OOM):** OpenSearch colapsa si se le piden muchos datos a la vez. En el Backend (FastAPI), todo endpoint que consulte a Wazuh debe usar **Paginación Defensiva (chunk_size <= 1000)** y **StreamingResponse** de Python (generadores) para evitar cargar el dataset completo en la memoria de la aplicación.
3. **Flujo de Red:** El Frontend (React) en Vercel jamás toca a Wazuh directamente. Todo pasa obligatoriamente por el proxy interno del Backend (FastAPI).

# 📖 Scrum & MkDocs Agile Standards (HoneyMetrics Docs)

Esta Skill define las reglas estrictas de redacción técnica, levantamiento de requerimientos y diagramación requeridas por el Director de Proyecto. Todo agente o desarrollador que altere la documentación debe acatar esto.

---

## 1. 🎯 Product Backlog Sin Sesgo Técnico
- **Enfoque de Negocio:** Queda **estrictamente prohibido** redactar el backlog en términos técnicos ("Implementar endpoint", "Crear tabla alerts").
- **Regla del "QUÉ" y no el "CÓMO":** Las descripciones del backlog deben expresar valor. Ej: *"El usuario debe poder solicitar la extracción de eventos y ser notificado cuando el archivo esté listo."*
- **Priorización:** Las Historias de Usuario se priorizan exclusivamente por el impacto real y el valor de negocio, nunca por la complejidad técnica de su implementación subyacente.

---

## 2. 🔪 Slicing Obligatorio (CRUD Dividido)
- **Prohibición de Macro-Historias:** Queda **prohibido** agrupar operaciones CRUD enteras en una sola HU (Ej: "HU-01: Gestionar usuarios").
- **División Atómica:** Todo módulo CRUD debe dividirse en 4 historias independientes: Listar, Crear, Editar, Eliminar.
- **Sintaxis Canónica Obligatoria:** 
  `Como <Rol> Quiero <Acción> Para <Beneficio de negocio>`
- **Desglose Técnico:** Dentro de la HU, en la sección de "Tareas de Desarrollo", se deben enumerar los detalles técnicos (Backend, Frontend, BD) necesarios para cumplir la historia.

---

## 3. 🎲 Estimaciones (Fibonacci Strict)
- Las estimaciones de Story Points solo pueden usar la **Serie de Fibonacci**: `1, 2, 3, 5, 8, 13, 21`.
- Si una Historia de Usuario supera los **13 Story Points**, se considera una "Épica encubierta" y **debe ser descompuesta** obligatoriamente en historias más pequeñas (Vertical Slicing).

---

## 4. 🧪 Behavior-Driven Development (Gherkin)
- Todos los Criterios de Aceptación dentro de una Historia de Usuario DEBEN seguir el patrón Gherkin:
  ```gherkin
  Dado que <contexto previo / estado del sistema>
  Cuando <el usuario realiza una acción>
  Entonces <resultado observable, medible y verificable>
  ```
- **Escenarios Mínimos:** Cada HU debe contar con al menos 2 escenarios BDD: El "Happy Path" (flujo ideal) y un "Error/Exception Path" (flujo alternativo de falla controlada).
- **Prohibido:** Redactar criterios de aceptación como simples bullet points genéricos sin estructura.

---

## 5. 🗺️ Diagramación Arquitectónica (Mermaid.js)
- **Cero Imágenes Estáticas:** Queda estrictamente prohibido usar imágenes PNG/JPG para diagramar arquitectura dentro de los archivos Markdown de MkDocs. Las imágenes (`/mockups/`) solo se usan para referencias visuales de UI.
- **Uso Obligatorio de Mermaid.js:**
  - **Diagramas de Secuencia:** Usar `sequenceDiagram` asegurando el tag `autonumber`.
  - **Flujos de Proceso:** Usar `flowchart TD` (Top-Down) o `flowchart LR` (Left-Right).
  - **Modelos Entidad-Relación:** Usar `erDiagram`.
  - **Máquinas de Estado:** Usar `stateDiagram-v2`.

---

## 6. 📁 Estructura de MkDocs
- Toda documentación estructurada debe seguir la jerarquía definida en el archivo raíz `mkdocs.yml`.
- Los sprints y las Historias de Usuario se alojan en `docs/sprints/`.
- Los diagramas de arquitectura en Mermaid se documentan centralizadamente en `docs/arquitectura/`.

# 🍯 HoneyMetrics: Plataforma Avanzada de Cyber Threat Intelligence (CTI)

## 1. El Origen: ¿De dónde nace la idea?
La idea de HoneyMetrics nació de una conversación muy reveladora. Mi hermano trabaja como consultor de ciberseguridad en **INDRA** y, charlando sobre su día a día, me compartió una problemática crítica en la industria: **el factor humano en el análisis de alertas**.

Él desplegó un *honeypot* (un servidor trampa) en nuestra red doméstica y comenzó a capturar datos en Wazuh. Sin embargo, la interfaz por defecto no ofrecía una lectura visual rápida y útil. Pero el problema real iba más allá del software: en las empresas, los analistas de seguridad Junior a menudo carecen de la experiencia necesaria para distinguir un ataque real de un "falso positivo". Peor aún, el exceso de alertas (fatiga de alertas) genera que, por pereza o agotamiento, los analistas ignoren reportes asumiendo que "no es nada grave". 

Ese sesgo humano es la puerta de entrada para los ataques más destructivos. Ahí vimos la oportunidad: **¿Y si creamos una plataforma que mastique esos datos, los grafique de forma intuitiva y filtre el ruido, ayudando a los analistas a no equivocarse?**

---

## 2. ¿Qué es HoneyMetrics?
**HoneyMetrics** es una plataforma de Inteligencia de Amenazas (CTI) diseñada para capturar, procesar y visualizar métricas de ciberataques en tiempo real. 

El concepto es simple pero poderoso:
- **Honey (La Trampa):** Usamos hardware de bajo costo (Orange Pi 5) para desplegar señuelos en la red. Los atacantes creen que están vulnerando un servidor real, pero en realidad están siendo estudiados.
- **Metrics (La Inteligencia):** Todo lo que hace el atacante se registra, se procesa y se envía a un Dashboard centralizado donde el ruido se convierte en gráficas claras, precisas y accionables.

---

## 3. El Problema que Resolvemos
1. **Fatiga de Alertas:** Los SIEMs tradicionales generan miles de logs incomprensibles.
2. **Falta de Experiencia (El error Junior):** Minimizar el margen de error humano de analistas que descartan falsos positivos o ignoran alertas reales por cansancio.
3. **Carencia de Visibilidad:** Dificultad para entender "quién nos ataca, cuándo y cómo".

---

## 4. Nuestra Arquitectura (El Motor del Proyecto)
Hemos diseñado HoneyMetrics bajo una arquitectura moderna, profesional y altamente escalable (API-First):

- **El Cerebro (Backend):** Desarrollado en **FastAPI** (Python). Es ultrarrápido, asíncrono y se encarga de procesar los datos masivos provenientes de la API de Wazuh (OpenSearch).
- **El Rostro (Frontend):** Construido con **React 18** y TailwindCSS. Un diseño "Dark Mode" (estilo *Glassmorphism*) enfocado en la experiencia de usuario (UX) para Centros de Operaciones de Seguridad (SOC). Todo el trabajo pesado de renderizar reportes PDF se hace del lado del cliente para no saturar el servidor.
- **El Ecosistema (Sensores):** Agentes Wazuh corriendo en placas Orange Pi 5, demostrando que se puede hacer ciberseguridad de alto nivel con eficiencia de recursos.

---

## 5. Enfoque Actual: Análisis de Datos (Entrega a 2 meses)
Para la entrega proyectada en dos meses, el proyecto tiene un enfoque estricto en el **Análisis y Visualización de Datos**. 

Sabemos que la Inteligencia Artificial es un campo complejo que requiere bases de datos sólidas y un entendimiento matemático profundo que aún estamos asimilando. Por lo tanto, en esta fase **no integraremos modelos predictivos de IA**, sino que nos enfocaremos en:
- **Dashboards Interactivos:** Gráficas de torta, líneas y barras generadas con *Plotly*.
- **Mapas de Calor (Heatmaps):** Visualización de las horas y días pico donde ocurren los ataques.
- **Top de Amenazas:** Ranking de las reglas de seguridad más violadas y las direcciones IP más hostiles.
- **Descarga de Evidencia:** Generación de reportes dinámicos para auditoría.

*En resumen: Estamos construyendo los cimientos perfectos (recolectando más de 165.000 eventos) para que, en un futuro, un modelo de Machine Learning tenga datos limpios y estructurados de dónde aprender.*

---

## 6. Articulación Institucional

Este proyecto no solo es un desafío técnico, sino que se alinea profundamente con la visión de la Universidad y las necesidades globales:

### Modelo MEDIT (Universidad de Cundinamarca)
HoneyMetrics se articula con la **Dimensión Translocal** del Modelo Educativo Digital Transmoderno (MEDIT). 
Actuamos como un "agente de transformación social que resuelve problemas desde lo local para la globalidad". La ciberseguridad es una amenaza mundial, pero estamos creando tecnología, talento y soluciones directamente desde nuestro territorio (Facatativá) para proteger infraestructuras digitales sin depender exclusivamente de licencias extranjeras costosas.

### Objetivos de Desarrollo Sostenible (ODS)
- **ODS 9 (Industria, Innovación e Infraestructura):** Aportamos innovación tecnológica para construir infraestructuras digitales resilientes, protegiendo los datos de las organizaciones frente a ciberataques.
- **ODS 16 (Paz, Justicia e Instituciones Sólidas):** Fomentamos la seguridad y la reducción del cibercrimen, dotando a las instituciones (públicas y privadas) de herramientas para defender su soberanía digital.

---

# 🌳 Commits Estratégicos y Autoría (Anti-IA Suspicion)

Esta Skill define cómo el agente debe comportarse al momento de guardar el código en Git dentro de los repositorios de HoneyMetrics, asegurando un historial limpio, auditable y que refleje un trabajo humano metódico.

## 1. La Regla de Oro del Versionamiento
El agente tiene total libertad para programar grandes bloques de código y probar funcionalidades completas de una sola vez. **Sin embargo**, al momento de subir los cambios, **ESTÁ ESTRICTAMENTE PROHIBIDO usar `git add .` o `git commit -a`**.

## 2. El Protocolo de Commits Fraccionados
Una vez que una funcionalidad (ej. un Endpoint, un CRUD) está probada y lista, el agente debe guiar al usuario para empaquetar los archivos en **bloques lógicos (Commits Atómicos)**.

El proceso debe ser el siguiente:
1. **Analizar los cambios:** El agente revisa qué archivos fueron creados o modificados.
2. **Proponer el Fraccionamiento:** El agente agrupa los archivos por su propósito (ej. Modelos de BD, Lógica de Negocio, Frontend UI, Documentación).
3. **Preguntar Autoría (Dinámica):** Por CADA bloque lógico, el agente DEBE preguntarle al usuario: *"¿A nombre de quién debe quedar este commit? ¿Tuyo, de tu compañero, o Co-Authored?"*

### Ejemplo del Flujo Correcto:
> **Agente:** "El desarrollo del Login está completo. Vamos a subirlo en 3 commits atómicos. Para el primer commit (Base de Datos), ¿quién es el autor?"
> 
> **Usuario:** "Ponlo a nombre de Juan Pablo."
> 
> **Agente:** "Perfecto. Ejecuta esto:
> `git add app/models/user.py app/schemas/user.py`
> `git commit --author="Juan Pablo Fonseca <correo@gmail.com>" -m "feat(db): crear modelos de usuario"`
> 
> Ahora, para el segundo commit (Lógica JWT), ¿quién es el autor?"

## 3. Formato de Mensajes (Conventional Commits)
Todos los commits deben seguir el estándar *Conventional Commits*:
- `feat:` (nuevas funcionalidades)
- `fix:` (solución de bugs)
- `docs:` (cambios en documentación / UML)
- `refactor:` (mejoras de código sin cambiar funcionalidad)
- `chore:` (tareas de mantenimiento, dependencias)

*Nota: Para aplicar overrides de autor, consultar la nota conceptual del usuario sobre `--author` y `Co-authored-by`.*
